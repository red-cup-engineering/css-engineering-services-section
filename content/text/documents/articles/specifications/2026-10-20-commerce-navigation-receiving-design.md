## Exact fixture stream lifecycle

Response fixture bodies are lazy consumer-driven standard Fetch ReadableStreams with queue strategy highWaterMark zero, never eager enqueue/close in start or fetch construction. Source-start is recorded when the fixture hook receives the actual Request. For a response with a permitted body, the first actual consumer pull yields exactly one Uint8Array containing all UTF-8 bodyText bytes; if there are no bytes, that first pull instead performs EOF completion. After a nonempty chunk, the next actual consumer pull performs EOF completion. EOF completion closes the stream, applies non-null completeAt to host clock, then records exactly one source-complete at that clock, in that order. Do not complete at response creation, enqueue, header inspection, consumer cancellation, releaseLock, or queued producer work. Thus response refusal before body consumption, including redirect/payment/MIME/HTTP refusal, has no source-complete and never applies completeAt. Body cancel alone is inert for source-complete/source-abort/clock; it permanently prevents later EOF completion. A target byte-limit abort after the sole chunk also has no source-complete and leaves completeAt unapplied. Request.signal abort records exactly one source-abort at current host time, cancels further fixture delivery and prevents EOF completion; repeated cancellation/abort does not duplicate it. A cancellation without signal abort emits no source-abort. Deliberate network-error rejects before a Response and never emits source-complete or applies completeAt. Deliberate until-aborted never supplies a Response or body, records its single source-abort only when the actual signal aborts, then rejects as abort stimulus without setting instrumentFailure; completeAt is unapplied. Native body-forbidden response statuses204/205/304 use actual null body, require empty bodyText at instrument admission, and never emit source-complete or apply completeAt; a nonempty bodyText for such a status is constructor-invalid fixture TypeError.
