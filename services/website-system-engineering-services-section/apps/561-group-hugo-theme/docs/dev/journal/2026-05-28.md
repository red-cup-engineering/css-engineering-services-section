# Reading Hugo as a category-theoretic system

This session opened the question: what would it look like to construct a website with Hugo using the same categorical discipline the rest of this project uses — explicit generators, declared restriction/extension relationships, and a lattice of kinds instead of convention-driven file lookup.
The answer is not "add category theory to Hugo."
Hugo *already is* a category-theoretic system; the structure is latent in its conventions.
The work is to make the latent structure explicit so it can be reasoned about, validated, and extended.

What follows is the load-bearing reading established this session.
The claims are stated as facts because they are observations about Hugo's actual behavior, falsifiable by running Hugo against a counter-example.
Open questions are listed separately at the end.

## Established facts about Hugo's existing categorical structure

### Hugo's layout lookup is a restriction lattice

When Hugo renders a page, it walks a specificity chain to find a layout.
The chain for a page of kind `single` in section `letters` with output format `html` is, in order: `layouts/letters/single.html` → `layouts/_default/single.html` → `layouts/_default/page.html` → theme equivalents → fallback.
Each step is a **restriction in scope**: more-specific names override more-general names.
Read in reverse, each step is an **extension**: a more general layout extends its applicability to cases not covered by the specific ones.

The "most specific match wins" rule is the universal property of a most-specific restriction in a lattice — Hugo's layout system is a finite distributive lattice with the lookup function as the join-irreducible projection.
The lattice is implicit in the file-naming convention; no part of `hugo.toml` declares the lattice structure.

### Frontmatter is type judgement

A page's frontmatter declares its position in Hugo's type space.
The fields `kind`, `type`, `layout`, and the page's filesystem path (which determines `section`) jointly index where the page lives in the multi-axis category of pages.
Hugo's layout lookup uses these as type indices: it treats `(section, kind, type, layout, format)` as a typed tuple and resolves the layout chain against that tuple.

The `type` field is the only one users routinely set explicitly.
Hugo's behavior on `type:` is exactly that of a discriminated union tag — pages with the same `type:` share layouts and frontmatter expectations.

### Taxonomies are functors with automatic term-page generation

The `[taxonomies]` config block declares functors from the page category to term sets.
`tag = "tags"` declares a functor `Page → Set(Tag)`.
Hugo automatically generates the inverse pages (the term pages listing all content tagged with each value) and the taxonomy page (the index of all tag values).
This automatic generation is the left adjoint to the forgetful functor that drops the tag axis.

Currently configured taxonomies: `tags`, `types`, `authors`.
Each is a separate functor; the resulting term-page tree is the colimit of their action on the corpus.

### Output formats are parallel rendering functors

`[outputs]` declares per-kind tuples of output formats: `home = ["html", "rss", "ttl", "jsonld", "jsonfeed"]`, `section = ["html", "rss", "ttl", "jsonld"]`, `page = ["html", "ttl", "jsonld"]`.
Each format is a separate rendering functor from the content category to a format-specific target category (HTML, RSS XML, Turtle RDF, JSON-LD, JSON Feed).

The `(Kind, Format)` grid is a 2D table of rendering cells.
Each cell needs a layout.
Hugo's layout lookup walks the (Kind, Format) axes independently — file naming encodes both — so the grid is already factored as a product.
Layouts for individual cells are at `layouts/_default/<kind>.<format>.html`.

The output formats `ttl`, `jsonld`, and `jsonfeed` are user-declared in `hugo.toml` (Hugo only ships `html`, `rss`, `json`, etc. by default).
Their existence in emsenn-net's config makes the site a semantic-web publication target: every page is a node in an RDF graph, rendered both human-readable (HTML with RDFa) and machine-readable (Turtle, JSON-LD).

### The semantic-web outputs realize the categorical view directly

The theme's `layouts/partials/json-ld.html`, `json-ld-home.html`, `json-ld-list.html`, and `rdfa-property.html` are concrete functors from content to RDF.
A page's frontmatter is the source object; the partial is the morphism; the JSON-LD/Turtle output is the target object.
The vocabulary at `static/vocab/index.ttl` is the codomain's identity description (the ontology against which all rendered terms are typed).

This is the place where the project's broader categorical commitments meet the website directly.
The frontmatter is a typed term; the layout-partial is a functor application; the rendered RDF is the image.
Every page emitted by emsenn-net is, by construction, a typed claim in a published knowledge graph.

## The piece that is implicit and would change if made explicit: the kind lattice

Hugo has a fixed set of built-in page kinds: `page`, `home`, `section`, `taxonomy`, `term`.
Users additionally use the `type:` frontmatter field to declare custom kinds (letter, essay, vocabulary-term, etc.).
There is no syntactic relationship between these custom types — no declaration that `letter ⊏ writing-piece ⊏ published-page`, no inheritance of frontmatter schema across kinds, no shared-layout chain that respects a declared hierarchy.

If the kind lattice were declared explicitly (location undecided — see open questions), three things would unify against it:

1. **Layout inheritance** would walk the declared lattice.
  A `letter` page missing a `single.html` would fall back to `writing-piece/single.html`, then `published-page/single.html`, then `page/single.html`.
  Hugo's existing convention only walks `<section>/_default/<built-in kind>`; declaring the lattice extends this to the user-declared kind axis.

2. **Frontmatter schema inheritance** would become possible.
  A JSON Schema for `letter` would `$ref` the schema for `writing-piece`, which would `$ref` `published-page`.
  Required fields would propagate down; build-time validation against the schema becomes a categorical type check.

3. **Output-format predicates would inherit.** A page rendered as `letter` in JSON-LD format would gain all RDF predicates declared by ancestor kinds, plus its own letter-specific ones.
  The `static/vocab/` ontology becomes the formal target of this inheritance chain.

All three of these are layouts/schemas/output-format declarations already, but they currently inherit independently or not at all.
Declaring the lattice once and having all three respect it is the structural unification.

## The generation chain among content kinds

This site's content kinds stand in a directed generation relation that operates over the authoring process rather than over kind specialization.
The relation established this session, with `→` read as "generates":

- `emsenn → babbles` — babbles are emsenn's first-order output, written directly, without intermediate processing.
- `(emsenn, babbles) → letters` — letters are second-order: emsenn applies authorial judgement to the accumulating babble corpus, lifting selected material into a publishable form addressed to a readership.
- `(babbles, letters) → terms` — terms are third-order: stabilized vocabulary distilled from the running corpus, the recurring concepts that the babbles and letters have, by accumulation, identified as load-bearing.
- `(babbles, letters, terms) → papers` and `papers → terms` — papers and terms form a coupled fixed-point.
  A paper is generated from the existing corpus including its current terms; writing the paper produces new terms (the paper's vocabulary contribution); those new terms feed back into the term layer.

The chain is monotonic in scope through the first three layers — each later kind narrows the input space — but becomes mutually recursive at the (terms, papers) pair.
This is not a design defect; it is how published scholarship actually works.
Papers use stable terms AND they introduce new ones; the term layer accumulates from both the running corpus AND from the formalization moves papers perform.
In the project's regime-tower framework ([[project_regime_tower]]), the (terms, papers) loop is a Scott-continuous closure: as the corpus accumulates, the pair settles toward a fixed point where every paper's defined terms appear in the term layer and every term has at least one citation.
Mid-corpus, neither side is closed — there are terms with no papers and papers introducing terms not yet stabilized.

The generation chain is distinct from the kind lattice discussed in the previous section.
The lattice answers "what is this a special case of?"
(a `letter` is a specialization of `dated-writing-piece`).
The chain answers "what was this generated from?"
(a `letter` is generated from babbles by emsenn's judgement).
A babble and a letter may be siblings in the lattice — both specializations of `dated-writing-piece` — while standing in a `babble → letter` arrow in the generation chain.
Both structures are real; both constrain how layouts, schemas, and RDF predicates should be organized; they are not identical and should not be conflated.

A consequence specific to this site: **terms are not imported from prior archives.** Terms are produced from this site's babbles, letters, and papers as the corpus is processed.
The 1,712-term corpus in `lab/archive/` records past term-extractions from earlier corpora; it is not the canonical source for this site's terms.
This site's terms emerge from this site's actual material, fresh.

## Connection to the project's foundational math

The active tree is building a foundation in which standard category theory recovers as a Scott-continuous shadow of predication category theory ([[project_gct_is_scott_shadow]]).
Hugo's layout lookup — the most-specific-match-wins rule walking a restriction lattice — is itself a Scott-continuous-shadow phenomenon.
The lookup is the join in the knowledge order on layout-evidence (more specific = more evidence-laden); the fallback chain is the directed set whose supremum is the most-specific match.

This means the work proposed here (declaring the kind lattice, having layouts/schemas/output-formats inherit it) is not an external imposition of category theory onto Hugo.
It is the recognition that Hugo's existing behavior is already that of a degenerate (Scott-continuous, Boolean-shadow) predicate category, and the explicit version is the same structure made visible and editable.
The categorical view does not change what Hugo does; it changes how the system describes what it does.

## Open questions

1. Where does the kind lattice live?
  Candidates: `hugo.toml` under `[params.kinds]` (ephemeral assertion, available to templates), `data/kinds.yaml` (build-time data available to layouts via `.
  Site.
  Data.kinds`), or as a tree of JSON Schema files inside the theme at `schemas/<kind>.schema.json` (validation contract, but Hugo doesn't natively consume it).
  Each storage choice commits to a different role: config / data / contract.

2. What is the minimum set of kinds for the current corpus?
  The content surface today is: 83 letters at `content/letters/`, 210 babbles at `content/babbles/`, standing pages (about, contact, legal, support), and an inline RDF vocabulary at `static/vocab/index.ttl`.
  Two of those (letter, babble) are user-declared kinds with their own section.
  Two further kinds are named in the generation chain but have no content yet: term and paper.
  Both will be produced from this site's own babble and letter corpus, not imported.
  A first-pass lattice has at minimum: `page` (the generic catch-all) plus the four user-declared kinds `babble`, `letter`, `term`, `paper`.
  The fact that letters and babbles share obvious structural ancestry — both are dated, authored, published, accumulating-over-time pieces — suggests their common ancestor (`dated-writing-piece`?
  `journal-entry`?) is a real intermediate kind, not an abstraction reach.
  Terms and papers may share their own ancestor (`scholarly-form`?
  `defined-vocabulary`?) — undetermined.

3. How does a user-declared kind lattice interact with Hugo's built-in kinds (`page`, `section`, `home`, `taxonomy`, `term`)?
  Built-in kinds are dimensional (every page is one of them); user kinds are typological (a `letter` is also a `page`).
  The lattice probably has the built-in kinds as a separate axis from the user-declared `type:` axis, with the (built-in × user) product being where layouts live.

4. Is the right next step to draft the lattice on paper (sketch the kinds and their restriction relationships for the current corpus) or to attempt to express one restriction in whichever storage location turns out to be right?
  The first is design work; the second is forcing the design to confront Hugo's actual constraints.

5. How do the generation chain and the kind lattice constrain each other?
  They are formally distinct (process-arrow vs specialization-order) but not independent.
  If two kinds stand in a generation arrow, they likely share an ancestor in the lattice — the producer's material gets refined, not transformed into something categorically alien.
  Letters share an ancestor with babbles because letters are made FROM babbles.
  Terms and papers may share an ancestor for the same reason.
  The exact shape of this constraint — whether generation arrows imply lattice arrows, or merely co-locate kinds under a shared ancestor — is undetermined.

## Status

This session: established the reading (sections 1–5 above), declared the generation chain among content kinds (`emsenn → babbles → letters → (terms ↔ papers)`), removed the cross-corpus module-mount infrastructure from emsenn-net's `hugo.toml`, built two concrete content corpora the lattice will need to describe — 83 letters at `content/letters/` and 210 babbles at `content/babbles/` — and located the relevant prior thought in `lab/` for the upcoming lab-rearrangement turn.
Terms and papers are named in the chain but have no content yet; they will be generated from this site's own babble and letter corpus rather than imported from prior archives.
Both letter and babble are dated, authored, published-over-time forms, structurally similar but differing in cadence (babbles are higher-frequency, often short, often timed to the minute; letters are lower-frequency, longer, addressed to a public readership).
They are the first two real kinds the lattice will have to distinguish AND find common ancestry for.
The prior thought search confirms: typed-relations-in-frontmatter, cyclic-dependency-as-feature, and term-defining-pages all pre-exist in the corpus; what this session adds is the explicit generation chain + restriction-lattice framing, and the bridge between those prior pieces and Hugo's actual structure.
No layout or schema work yet — the lattice is still un-drawn.
